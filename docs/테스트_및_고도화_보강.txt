## 테스트 목적

PoC 단계에서 구현한 ReAct 에이전트의 RAG 검색 정확도, 예외 처리 동작, 응답 성능이
실제 운영 조건에서 의도대로 동작하는지 검증하고, 발견된 문제를 고도화하여 E2E 단계로
이어질 수 있는 기반을 확보한다.

## 주요 문제 해결 및 기술 리서치 (테스트 단계)

테스트 과정에서 발견된 엣지 케이스(Edge Case)와 성능 병목을 해결하기 위해
리서치하고 적용한 방법을 기록합니다.

| **이슈 구분** | **문제 상황 및 원인** | **리서치 및 해결 과정 (Reference & Solution)** |
|------------|------------------|---------------------------------------------|
| **품질/환각** | RAG가 도메인 외 품목(예: 포틀랜드 시멘트)을 반도체 문서에 강제 매칭시켜 오분류된 HS-Code를 근거 있는 것처럼 반환. 원인: `text-embedding-3-small`은 "관련 없음"을 판단하지 않고 항상 가장 가까운 문서를 반환하며, 임계값 0.30이 너무 낮아 무관한 문서도 통과 | **리서치:** 코사인 유사도 기반 RAG의 "Nearest Neighbor 특성" 분석 — 도메인 외 쿼리도 반드시 상위 k개가 반환됨을 확인. 임계값(Threshold)이 품질 관문 역할을 함을 파악  **적용:** ① 임계값 0.30 → 0.45로 상향 (UI 슬라이더 기본값 변경) ② 에이전트 프롬프트에 "검색 근거와 품목이 불일치할 경우 오분류 경고를 명시하라" 지시 추가 → 에이전트가 스스로 "오분류 가능성이 매우 높습니다. 관세사 재확인 필수" 경고를 답변에 포함하도록 동작 |
| **속도/지연** | HS-Code 추천 응답 시간이 7~25초로 길게 측정됨. 원인: ReAct 루프 구조상 search_hs_code_rag → query_tax_rate 도구를 순차 호출하며, 각 호출마다 Azure OpenAI API 왕복 지연이 누적됨. Pinecone 임베딩 생성도 최초 호출 시 콜드 스타트 발생 | **리서치:** LangChain AgentExecutor의 도구 순차 호출 구조 분석 — ReAct 방식은 Thought→Action→Observation 1사이클에 LLM 호출 1회가 필수로 수반됨. Render 무료 플랜 서버 위치(미국)와 Azure OpenAI 엔드포인트 간 네트워크 지연도 확인  **적용:** ① 벡터스토어 객체를 전역 캐싱(`_vectorstore` 싱글톤)하여 콜드 스타트 제거 ② 임베딩 모델 객체도 동일하게 캐싱 적용 → 동일 세션 내 2회차 요청부터 응답 시간 단축 확인 |
| **보안/가드레일** | RAG Fallback 발생 시 LLM이 근거 문서 없이 자체 지식만으로 HS-Code를 추천하여 사용자가 이를 신뢰할 수 있는 결과로 오인할 위험 존재. 실제로 Fallback 상태에서도 구체적인 HS-Code 번호가 포함된 정상 결과처럼 보이는 답변이 출력됨 | **리서치:** RAG 시스템의 Fallback 투명성(Transparency) 설계 원칙 검토 — 사용자에게 결과의 신뢰 수준을 명시적으로 표시해야 한다는 AI 가이드라인 확인  **적용:** ① UI에 Fallback 여부를 별도 지표(메트릭 카드)로 표시 ② Fallback 발생 시 황색 경고 배너("RAG 문서 근거 없음 — LLM 지식 기반 추천. 반드시 전문가 확인 필요") 출력 ③ Fallback 원인 코드(`유사도 X.XX < 임계값 Y.YY`)를 UI에 노출하여 추적 가능하도록 설계 |

## 1. LLM 답변 품질 평가 및 개선

| 항목 | 내용 |
|------|------|
| **평가 대상 기능** | RAG 기반 HS-Code 추천 정확도 및 근거 문서 활용 여부 |
| **테스트 케이스 구분** | ① 정상 추천 (도메인 내 품목) ② 문서 미매칭 (Fallback) ③ 도메인 외 강제 매칭 ④ 근거 충돌 (Conflict) |
| **평가 방식** | 반도체 대표 품목 5건을 수동 입력, Fallback 발생 여부·근거 품질 점수(0~8점)·추천 HS-Code 타당성 직접 확인. 근거 품질 점수(문서명·페이지·인용 문장·유사도 기준 8점 만점)를 대리 지표로 활용 |
| **평가 결과 (개선 전)** | Fallback=예, 근거 품질 0.0/8.0점 — 슬라이더 임계값(0.10)이 도구에 전달되지 않아 도구 기본값 0.75가 적용되는 버그로 항상 Fallback 발생 |
| **개선 조치** | ① `_format_question()`에 `similarity_threshold` 값을 LLM 프롬프트에 포함시켜 도구 호출 시 전달되도록 수정 ② 도구 기본 임계값 0.75 → 0.30으로 하향 ③ ReAct 프롬프트에 올바른 Action Input 예시 명시 ④ 근거 품질 채점 로직(문서명·페이지·인용·유사도 항목별 부분 점수) 구현 |
| **평가 결과 (개선 후)** | Fallback=아니오, 근거 품질 6.0/8.0점 달성. 에이전트가 RAG 문서 근거를 인용하며 HS-Code 추천 및 오분류 경고를 스스로 판단하여 출력 |
| **성공 기준** | Top-1 추천 코드 앞 4자리(호) 일치 → 성공 / Top-3 내 포함 → 부분 성공 / 근거 품질 ≥ 5.0/8.0 → 품질 요건 충족 |

**개선 전/후 비교:**

| 측정 항목 | 개선 전 | 개선 후 |
|---------|--------|--------|
| FOUP Fallback 여부 | 예 (버그) | 아니오 |
| 근거 품질 점수 | 0.0/8.0 | 6.0/8.0 |
| Top-1 코드 정확도 | 측정 불가 | 3923100000 일치 (성공) |
| 신뢰도 레이블 | 항상 "낮음" | "중간" (유사도 0.47 ≥ 0.45) |

## 2. 성능 및 비용 최적화

| 항목 | 내용 |
|------|------|
| **기존 병목** | 최초 요청 시 Pinecone 연결·임베딩 모델 로드가 매번 발생하여 응답 시간 최대 25초 소요. ReAct 루프 내 LLM 호출이 Thought 단계마다 추가되어 지연 누적 |
| **개선 전략** | 벡터스토어·임베딩 모델 객체 전역 캐싱(싱글톤 패턴) 적용으로 콜드 스타트 제거 |
| **적용 기술** | Python 전역 변수(`_vectorstore`, `_embeddings`)를 싱글톤으로 선언, 최초 1회만 Pinecone 연결 및 임베딩 모델 초기화 후 이후 요청에서 재사용. `reset_vectorstore_cache()` 함수로 수동 초기화 지원 |
| **개선 결과** | 동일 세션 내 2회차 요청부터 Pinecone 연결 오버헤드 제거. 응답 시간 25초 → 7~10초 수준으로 단축. LLM 비용 절감을 위해 Azure OpenAI(gpt-4.1) 우선 사용, 미설정 시 Claude Sonnet으로 자동 Fallback하는 이중화 구조 적용 |

**응답 시간 개선 비교:**

| 조건 | 개선 전 | 개선 후 |
|------|--------|--------|
| 세션 내 첫 번째 요청 | 15~25초 | 10~15초 |
| 세션 내 두 번째 이후 요청 | 15~25초 (매번 동일) | 7~10초 (캐싱 효과) |
| Render 배포 콜드 스타트 | 20~30초 | 15~20초 (모델 초기화만 소요) |

## 3. 예외 처리 및 가드레일

| 항목 | 내용 |
|------|------|
| **차단 대상** | ① RAG 미매칭 시 근거 없는 추천 신뢰 오인 ② LLM의 도구 호출 인자 오형식(Malformed Tool Call) ③ 도메인 외 품목의 무관한 문서 강제 매칭 |
| **탐지 방식** | ① 유사도 임계값 게이팅: 최고 유사도가 임계값 미만이면 `fallback=True` 반환 ② 도구 입력값 방어 파싱: `product_name`이 JSON 문자열일 경우 자동 분해 처리 ③ 근거 품질 점수(0~8점)로 답변 신뢰도 정량화 |
| **대응 로직** | ① Fallback 발생 시 황색 경고 배너("RAG 문서 근거 없음 — LLM 지식 기반 추천") UI 출력 ② Fallback 원인 코드(`유사도 X.XX < 임계값 Y.YY`) 화면 표시 ③ 에이전트 프롬프트에 "검색 근거와 품목 불일치 시 오분류 경고 명시" 지시 삽입 → 에이전트 자체 판단으로 경고 포함 ④ 관세사 재확인 면책 고지 문구 답변 하단 고정 출력 |
| **테스트 결과** | 도메인 외 품목(시멘트, 섬유 등) 입력 시 에이전트가 "오분류 가능성 높음, 관세사 재확인 필수" 경고를 자율 판단으로 포함. Fallback 경고 배너 및 원인 코드 정상 출력 확인 |

**상태별 실제 응답 정책 및 검증 결과:**

| 상태 | 조건 | UI 응답 | 실제 동작 확인 |
|------|------|---------|-------------|
| 정상 (High Confidence) | fallback=False, conflict=False, 유사도≥임계값 | 경고 없이 후보·근거 표시 | FOUP 입력 시 정상 표시 확인 |
| 충돌 (Conflict) | fallback=False, conflict_flag=True | 주황 배너 "⚠️ 분류 충돌 감지 — TYPE-X" | 포토마스크 입력 시 TYPE-1 배너 출력 확인 |
| Fallback (저신뢰) | fallback=True | 황색 배너 "RAG 문서 근거 없음", 근거품질 0.0 고정 | 희석냉동기·시멘트 입력 시 배너 출력 확인 |
| 감사 로그 오류 | Top-1 외 코드 선택 + 수정 사유 미입력 | `saved=False`, 오류 메시지 반환 | save_audit_log 직접 호출로 수정 사유 필수 검증 동작 확인 |

## 5. 남은 한계 및 E2E 단계 과제

| 한계 항목 | 현황 | E2E 단계 방향 |
|---------|------|-------------|
| 참조 문서 커버리지 부족 | TXT 11개(242벡터)만 적재, HS 4~6자리 정밀 분류 불가 | PDF 규정집 추가 적재, 벡터 수 1,000개 이상으로 확대 |
| 도메인 외 품목 완전 차단 불가 | 임계값 0.45로 완화했으나 경계값 품목(0.40~0.50)은 여전히 오매칭 위험 | 류별 도메인 필터링 또는 도메인 분류 사전 단계 추가 |
| 충돌 시 추가 질문(Clarification) 미구현 | 충돌 배너만 표시, 에이전트가 사용자에게 재질/용도 추가 확인을 요청하는 흐름 없음 | clarification.py 도구 활용, 충돌 시 자동 질문 생성 |
| UNI-PASS API 미연동 | 정적 세율 테이블(6개 류)만 사용, 실시간 관세율 조회 불가 | API 키 발급 후 실제 연동, 동적 세율 반환 구현 |
| 응답 시간 | 7~10초 수준 (LLM API 호출 포함), 실시간 서비스 기준 초과 | 스트리밍 응답 적용 또는 도구 병렬 호출 구조 검토 |
